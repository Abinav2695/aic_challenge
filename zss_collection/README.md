# zss_collection — AIC Data Collection Pipeline

ROS 2 package that drives the UR5e arm through autonomous insertion episodes
and records them as a [LeRobot](https://huggingface.co/docs/lerobot) dataset.

```
zss_collection/
├── scripts/
│   ├── collect_orch.sh   # Orchestrator — runs inside aic-eval Docker
│   └── node.sh           # Helper to loop node_once for a batch
├── zss_collection/
│   ├── config.py         # ControllerParams, InsertionConfig, RecordingConfig, SessionConfig, TrialConfig
│   ├── action.py         # 7-dim delta-pose action builder + MotionUpdate helper
│   ├── obs.py            # 32-dim observation builder + named slice constants
│   ├── metrics.py        # Per-episode quality tracking (force, path length, contacts)
│   ├── recorder.py       # LeRobotDataset wrapper (begin_episode → add_frame → end_episode)
│   ├── node.py           # Multi-episode ROS 2 node (loops until "shutdown")
│   ├── node_once.py      # Single-episode ROS 2 node (exits after one episode)
│   └── controllers/
│       ├── waypoint.py   # WaypointController (original)
│       └── waypoint_2.py # WaypointController2 (current, used by node_once)
```

> All `pixi run` / `ros2 run` commands must be executed from `~/ws_aic/src/aic/`
> with the pixi environment active (`pixi shell`).

---

## Architecture

Collection uses a **two-process design** — orchestrator and collection node run
in separate terminals and communicate over ROS 2 topics:

```
┌─────────────────────────────────┐       ┌──────────────────────────────┐
│  Terminal A  (aic-eval Docker)  │       │  Terminal B  (pixi shell)    │
│                                 │       │                              │
│  collect_orch.sh                │       │  ros2 run zss_collection     │
│                                 │       │      collection_node         │
│  For each trial:                │       │                              │
│   1. Launch Gazebo scene        │       │  IDLE ──────────────────────►│
│   2. Pub scene_metadata ───────►│──────►│  RESETTING (TF lookup)      │
│   3. Wait for episode_event ◄───│◄──────│  COLLECTING (waypoint ctrl) │
│   4. Cleanup Gazebo             │       │  DONE → save → IDLE         │
│                                 │       │                              │
│  After all trials:              │       │                              │
│   5. Pub "shutdown" ───────────►│──────►│  finalize() → exit          │
└─────────────────────────────────┘       └──────────────────────────────┘
```

### ROS 2 topic interface

| Topic | Direction | Type | Description |
|-------|-----------|------|-------------|
| `/data_collection/scene_metadata` | Orch → Node | `String` (JSON, latched) | Per-trial target info |
| `/data_collection/episode_event` | Node → Orch | `String` (latched) | `"collecting"` / `"done"` / `"skip"` |
| `/data_collection/orch_control` | Orch → Node | `String` (latched) | `"shutdown"` after all trials |

## Step 1 — Generate a Batch Config

Scene configs live in `zss_data/configs/` and are generated by
`zss_data/zss_data/scene_randomize.py`. Each batch directory contains a
`launch_manifest.json` that `collect_orch.sh` reads.

```bash
cd ~/ws_aic/src/aic
pixi run python -m zss_data.scene_randomize \
    --batch-id batch_012 \
    --num-trials 25 \
    --plug-types sfp \
    --min-nic 1 --max-nic 2 \
    --min-sc-ports 0 --max-sc-ports 2 \
    --tight-board-pose \
    --seed 112
```

> ⚠️ Output goes to the pixi site-packages path. Copy the result manually:
> ```bash
> cp -r .pixi/envs/default/lib/python3.12/site-packages/configs/batch_012 \
>        ~/ws_aic/src/aic/zss_data/configs/batch_012
> ```

## Step 2 — Run Data Collection

### Terminal A — Start the collection node (pixi shell)

**Multi-episode node** — stays alive for the whole batch, loops back to IDLE
after each episode:

```bash
cd ~/ws_aic/src/aic
source ~/ws_aic/install/setup.bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp

pixi run ros2 run zss_collection collection_node --ros-args \
    -p batch_id:=batch_012 \
    -p dataset_root:=/home/abinav2695/datasets_new \
    -p record_images:=false \
    -p use_sim_time:=true
```

With camera recording:

```bash
pixi run ros2 run zss_collection collection_node --ros-args \
    -p batch_id:=batch_012 \
    -p dataset_root:=/home/abinav2695/datasets_new \
    -p record_images:=true \
    -p use_sim_time:=true
```

**Single-episode node** — exits cleanly after one episode (useful for debugging
or looping externally with `node.sh`):

```bash
pixi run ros2 run zss_collection collection_node_once --ros-args \
    -p batch_id:=batch_012 \
    -p dataset_root:=/home/abinav2695/datasets_new \
    -p record_images:=false \
    -p use_sim_time:=true
```

#### Node ROS 2 parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `batch_id` | `""` | Sub-folder under `dataset_root`; **required** |
| `dataset_root` | `~/datasets` | Root directory for all datasets |
| `record_images` | `true` (node) / `true` (node_once) | Enable camera video recording |
| `use_sim_time` | *(from launch)* | Must match Gazebo clock |

### Terminal B — Run the orchestrator (aic-eval Docker)

```bash
distrobox enter -r aic_eval   # or: docker exec -it aic_eval bash

cd ~/ws_aic/src/aic
export RMW_IMPLEMENTATION=rmw_zenoh_cpp

# Interactive (default): operator confirms each trial
bash zss_collection/scripts/collect_orch.sh \
    zss_data/configs/batch_012/launch_manifest.json \
    --batch-id batch_012

# Fully automatic (no prompts)
bash zss_collection/scripts/collect_orch.sh \
    zss_data/configs/batch_012/launch_manifest.json \
    --batch-id batch_012 \
    --auto

# Resume from trial 10 if interrupted
bash zss_collection/scripts/collect_orch.sh \
    zss_data/configs/batch_012/launch_manifest.json \
    --batch-id batch_012 \
    --auto \
    --start-from 10
```

#### Orchestrator flags

| Flag | Default | Description |
|------|---------|-------------|
| `--batch-id ID` | *(required)* | Must match collection node `-p batch_id` |
| `--auto` | off | Skip operator prompts; wait for `episode_event` signal |
| `--start-from N` | 0 | Resume from trial index N |
| `--settle-time SECS` | 15 | Wait after scene launch before checking controller |
| `--episode-timeout SECS` | 600 | Max wait for episode done in auto mode |
| `--dry-run` | off | Print commands without executing |

#### Interactive keyboard controls

| When | Key | Action |
|------|-----|--------|
| Pre-launch | `ENTER` | Launch trial |
| Pre-launch | `s` | Skip trial |
| Pre-launch | `q` | Quit orchestrator |
| Post-launch (manual mode) | `ENTER` | Episode done — save |
| Post-launch (manual mode) | `s` | Skip/discard episode |
| Post-launch (manual mode) | `q` | Quit orchestrator |

## Observation & Action Space

### Observation — `observation.state` (32-dim float32)

| Slice | Dims | Field | Units |
|-------|------|-------|-------|
| `TCP_POSE_SLICE` | 0–6 | `tcp_pose` — position (x,y,z) + quaternion (qx,qy,qz,qw) | m, — |
| `TCP_VEL_SLICE` | 7–12 | `tcp_velocity` — linear (x,y,z) + angular (x,y,z) | m/s, rad/s |
| `TCP_ERR_SLICE` | 13–18 | `tcp_error` — Cartesian error (x,y,z,rx,ry,rz) | m, rad |
| `JOINT_SLICE` | 19–25 | `joint_positions` — joints 0–5 (rad) + pad 0.0 for j6 | rad |
| `FORCE_SLICE` | 26–28 | `compensated_force` — FTS force minus tare (x,y,z) | N |
| `TORQUE_SLICE` | 29–31 | `compensated_torque` — FTS torque minus tare (x,y,z) | N·m |

Named slice constants are defined in `obs.py` and should be used in model
architectures instead of bare integers, e.g. for separate encoder heads:

```python
from zss_collection.obs import TCP_POSE_SLICE, FORCE_SLICE
proprio = obs[TCP_POSE_SLICE]   # (7,)
contact = obs[FORCE_SLICE]      # (3,)
```

> **j6 (dim 25):** Always 0.0 — gripper stays fixed during insertion.  
> **Force/torque (dims 26–31):** Tared by the eval engine before each trial.
> Peak safe insertion force is ~20 N; the AIC penalty activates above 20 N for >1 s.

### Action — `action` (7-dim float32, **delta pose in TCP frame**)

| Dims | Field | Units |
|------|-------|-------|
| 0–2 | `delta_position` — Δx, Δy, Δz in current TCP frame | m |
| 3–6 | `delta_orientation` — Δqx, Δqy, Δqz, Δqw in TCP frame | — |

The action is an **incremental delta** expressed in the current TCP frame,
not an absolute target in `base_link`. This choice makes the representation
**board-position-invariant**: the same insertion motion at two different board
locations produces nearly identical action sequences. It also means demonstrations
from different scenes and different NIC cards are directly comparable without
any post-processing.

At inference time, send the predicted delta as `MODE_POSITION` in the
`gripper/tcp` frame — the Cartesian impedance controller interprets it as
an incremental move from the current pose.

> Stiffness is a **fixed controller parameter** (`ControllerParams.stiffness`),
> not part of the action. This keeps the model output small and prevents the
> policy from varying impedance, which would complicate force analysis.

### Camera images (when `record_images:=true`)

Three cameras captured as MP4 video (AV1 codec), stored separately from the
parquet frames:

| Key | Stored resolution | Description |
|-----|-------------------|-------------|
| `observation.images.left_camera` | 256×288×3 | Left view of the task board |
| `observation.images.center_camera` | 256×288×3 | Centre / over-shoulder view |
| `observation.images.right_camera` | 256×288×3 | Right view of the task board |

Native resolution is 1024×1152; `image_scale: 0.25` is applied at recording
time. Videos live at:
```
<dataset_root>/<batch_id>/videos/<key>/chunk-000/file-NNN.mp4
```

### Task description (language conditioning)

Each episode is tagged with a natural-language task string stored in
`meta/tasks.parquet`, e.g.:

```
"Insert sfp cable into nic_card_mount_1 sfp_port_0"
```

This string is the **only signal that distinguishes which port and card is
the target** at training time — the port TF is not available during evaluation.

| Policy | Consumes task string | Use when |
|--------|---------------------|----------|
| `act`, `diffusion` | ❌ No | Single-task batches (one port/card) |
| `smolvla`, `pi0` | ✅ Yes | Multi-port / multi-card batches |

> If your batch targets multiple ports or NIC cards, train with a
> language-conditioned policy (`smolvla` or `pi0`). A plain ACT model
> cannot distinguish targets and will average over all of them.

## Insertion Phase Sequence

The waypoint controller drives the robot through five phases, all recorded:

```
PRE_APPROACH → APPROACH → CORRECT → DESCEND → HOLD → DONE
```

| Phase | Duration | What happens |
|-------|----------|--------------|
| `PRE_APPROACH` | ~3.5 s (70 ticks) | Moves to overview height above board centre — all NIC mounts visible in cameras. Teaches policy to visually identify the target |
| `APPROACH` | ~5 s (100 ticks) | Ramps TCP toward port at `approach_z_offset` (0.20 m above port) |
| `CORRECT` | up to 10 s (200 ticks) | XY integrator loop — corrects lateral error until within 20 mm of port axis |
| `DESCEND` | variable | Steps down 0.8 mm/tick until insertion event fires or 40 N force limit |
| `HOLD` | 5 s (100 ticks) | Maintains inserted pose; records confirmation frames |

Key `InsertionConfig` values (in `config.py`):

| Parameter | Value | Meaning |
|-----------|-------|---------|
| `tick_rate_s` | 0.05 s | 20 Hz recording |
| `approach_z_offset` | 0.20 m | Height above port at end of approach |
| `descend_step_m` | 0.0008 m/tick | 16 mm/s descent rate |
| `insert_force_limit_n` | 40 N | Pause descent above this force |
| `max_episode_ticks` | 3600 | 3 min hard timeout |

## Training with LeRobot

### Minimal ACT training (single-task batch)

```bash
cd ~/ws_aic/src/aic
pixi run lerobot-train \
    --dataset.repo_id=local/batch_012 \
    --dataset.root=/home/abinav2695/datasets_new/batch_012 \
    --policy.type=act \
    --policy.chunk_size=100 \
    --policy.n_action_steps=100 \
    --output_dir=outputs/train/act_batch_012 \
    --job_name=act_batch_012 \
    --batch_size=16 \
    --steps=100000 \
    --log_freq=250 \
    --save_freq=10000 \
    --policy.device=cuda \
    --seed=42 \
    --wandb.enable=true \
    --wandb.project=aic_sfp_insertion
```

Key ACT hyperparameters:

| Parameter | Recommended | Rationale |
|-----------|-------------|-----------|
| `chunk_size` | 100 | 5 s action window at 20 Hz |
| `n_action_steps` | 100 | Execute full chunk before re-querying |
| `batch_size` | 16 | Stable for ~12 k frames; increase if VRAM allows |
| `steps` | 100 000 | ACT needs many gradient steps on small datasets |

### SmolVLA training (multi-port or multi-card batch)

```bash
cd ~/ws_aic/src/aic
pixi run lerobot-train \
    --dataset.repo_id=local/batch_multi \
    --dataset.root=/home/abinav2695/datasets_new/batch_multi \
    --policy.type=smolvla \
    --output_dir=outputs/train/smolvla_batch_multi \
    --job_name=smolvla_batch_multi \
    --batch_size=8 \
    --steps=100000 \
    --policy.device=cuda \
    --wandb.enable=true \
    --wandb.project=aic_sfp_insertion
```

SmolVLA reads the per-episode task string
(`"Insert sfp cable into nic_card_mount_1 sfp_port_0"`) and conditions every
action prediction on it — the model learns to go to the **correct** port.

### Using a trained checkpoint

In `zss_policy/` (or `aic_example_policies/ros/RunACT.py`), replace the
HuggingFace download with your local checkpoint path:

```python
# Replace snapshot_download(...) with:
policy_path = Path(
    "~/ws_aic/src/aic/outputs/train/act_batch_012/checkpoints/100000"
).expanduser()
```

The checkpoint directory contains:
- `config.json` — policy config
- `model.safetensors` — model weights
- `policy_preprocessor_step_3_normalizer_processor.safetensors` — normalisation stats

> ⚠️ **Action space mismatch with `RunACT.py`:** The reference policy uses a
> 7-dim **absolute pose + stiffness** action, while `zss_collection` records a
> 7-dim **delta pose in TCP frame**. When writing your inference node, send
> predicted deltas as `MODE_POSITION` in the `gripper/tcp` frame rather than
> the `base_link` frame.
